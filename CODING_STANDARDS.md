# Coding standards

Read by the reviewer agent (`/code-review`), not by the builder. Judgement calls only: anything a tool can check belongs in a tool, not here. Keep this file short. Add a rule when a review misses something; remove one that only adds noise.

## Don't report

These already run in the pre-commit hook or CI. Skip anything they catch.

- `npm run lint`: ESLint, the frozen-test rules in `frozen/`, and `scripts/check-aws-calls.mjs` (an AWS CLI call in a workflow that would read a refusal as "none")
- `npm run format:check`: Prettier
- `npm run typecheck`: TypeScript
- `npm test`: Vitest
- `npm run secrets`: secretlint
- The frozen acceptance tests in `frozen/`, run by `verify.yml`
- Migrations that remove things: `deploy.yml` refuses them
- Anything in `frozen/`, `drizzle/` (generated) or `package-lock.json`

## Reporting bar

- Report only what you can show: cite `file:line` and say what goes wrong.
- If you're not sure, leave it out.

## Rules

### Every write survives a retry

Any write may run twice. A write must be an upsert keyed by a client-generated ID, inside `transactionWithRetry`.

- Bad: `db.insert(orders).values({ total })`, with the ID generated by the database
- Good: `tx.insert(orders).values({ id, total }).onConflictDoUpdate({ target: orders.id, ... })` inside `transactionWithRetry`, with `id` from the client

Why: a retried plain insert creates duplicates.

### A refusal isn't "nothing there"

When code reads an AWS call's failure or empty answer as "none" (no environment, no state, nothing to remove), it must tell an access refusal apart from absence, and fail on a refusal. `check-aws-calls.mjs` catches the shell shapes in workflows. This rule covers the rest: SDK calls in `src/` or `frozen/helpers/`, a `catch` that returns an empty list, and a shell shape the check can't see.

- Bad: `catch (e) { return []; }` around a list call; `if aws s3api head-object ...; then`
- Good: catch only the "not found" error by name and rethrow the rest; `if ! keys=$(aws s3api list-objects-v2 ...); then exit 1; fi`

Why: under the Budgets action's deny-all, both teardowns went green and left resources running (phase F, #64).

### Seed data is fake

`src/db/seed-data.ts` holds made-up data only: no real names, emails or addresses.

Why: it loads on every portfolio site, which is public.

### Comments give reasons, not narration

In the diff, flag a comment that:

- narrates the change, the chat, the plan or an old version ("Updated to use X", "as requested", "removed the old cache")
- doesn't match the code next to it

Outside the diff, flag a comment the change made false: when the diff changes what a function, type or route does, check comments that describe it (at its callers, its definition, and in docs). Cite the comment's `file:line` and the change that broke it.

Don't flag a comment that gives a reason (a constraint, a workaround, an invariant). Don't flag the style of comments the diff didn't touch.

Why: the next agent believes comments over code.

### The first render matches the prerendered HTML

Pages are prerendered at build time and hydrated in the browser, so a component's first render must give the same output in both places. Flag anything that reads browser-only or time-dependent values during render: `new Date()`, `toLocale*String()`, `window`, `document`, `navigator`, `location`, `localStorage`, `matchMedia`, `typeof window`, or `import.meta.env.SSR`. The lint's `purity` rule only catches `Date.now`, `performance.now` and `Math.random`. Also flag initial state that differs between the build and the browser, and any `suppressHydrationWarning`.

- Bad: `const [dark] = useState(matchMedia("(prefers-color-scheme: dark)").matches)`; `{typeof window !== "undefined" && <ChatTab />}`
- Good: theme from a CSS `prefers-color-scheme` media query; browser-only reads in `useEffect` or an event handler; browser-only UI behind `use(browser())` inside `<Suspense>`

Why: in production React 19 doesn't log or repair a mismatched attribute, so the build's value silently stays in the DOM. No frozen test catches that, so review has to. A text mismatch does surface, as page error #418, but only after it has failed a run.

### Effects survive running twice and never throw

An effect that fetches needs a cleanup that ignores stale results, and it must handle failure by rendering a state, not by throwing.

- Bad: `useEffect(() => { fetch("/api/health").then(r => r.json()).then(setStatus) }, [])`
- Good: an `ignore` flag or `AbortController` in the cleanup, and a `.catch` that sets a failure state (an abort included)

Why: Strict Mode runs effects twice in development, hydration included, so a fetch with no cleanup races itself. In production, an unhandled rejection (a network error or an abort) becomes a page error, which fails the frozen console check.
