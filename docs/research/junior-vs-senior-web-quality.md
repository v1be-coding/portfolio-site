# What separates a new developer's website from an experienced one's, and what a frozen test can check

Research notes for the spec, gathered 2026-11-17. The site is a React + Vite static frontend on CloudFront/Cloudflare, with an AWS Lambda API (`/api/health`, `/api/chat`). Frozen Playwright tests are written from the spec before the build, with no screenshot baselines. Test files must be straight-line code (no `if`, `try` or `return`, and no loose matchers). Helpers in `frozen/helpers/` may hold logic and import libraries. The tests run against a deployed branch environment, and `smoke/` also runs against production (`frozen/README.md`). The current config runs `workers: 1` with `retries: 1` (`frozen/playwright.config.ts`).

Conventions in this file:

- Each claim links to its source. Text in quotation marks is quoted from that source.
- **Inference:** marks my own reasoning, which no source states.
- **Practice:** marks guidance from an engineering organisation, such as a government digital service. It's evidence of what experienced teams do, not a standard.
- "Branch" means the acceptance run on a branch environment. "Prod smoke" means `smoke/`, which also runs on production.

## TL;DR

- **No primary source defines "junior vs senior" website quality.** The search found career-advice blogs only, which aren't credible enough to cite. What standards bodies and experienced teams _do_ document is a set of defaults that a careful builder sets on purpose and a new one leaves alone: security headers, cache headers, a real 404 status, `lang`, a unique title and description per page, a visible focus ring, reflow at 320px, sized images, and a clean console. **Inference:** this is the most testable form of the junior/senior difference, because each of these defaults is an observable fact about the deployed site.
- **Most of those markers can be checked deterministically** by asserting on headers, HTTP statuses, the DOM and computed styles. Examples are `expect(headers['x-content-type-options']).toBe('nosniff')`, `expect(await horizontalOverflow(page)).toBe(0)` at 320px, and `expect(axeViolations).toEqual([])`.
- **Automated accessibility testing is partial.** Deque says its axe rules found "57.38% of total issues" in first-time audits ([Deque](https://www.deque.com/automated-accessibility-testing-coverage/)). In GDS's 2017 test, the best single tool found 41% of 143 planted barriers, and all the tools combined found 71% ([GDS](https://accessibility.blog.gov.uk/2017/02/24/what-we-found-when-we-tested-tools-on-the-worlds-least-accessible-webpage/)). So add a few keyboard and focus tests on top of axe.
- **Don't gate on the Lighthouse Performance score.** Google says that score varies with "changes in underlying conditions" ([Chrome](https://developer.chrome.com/docs/lighthouse/performance/performance-scoring)), and that even "The median Lighthouse score of 5 runs is twice as stable as 1 run" ([Lighthouse variability](https://github.com/GoogleChrome/lighthouse/blob/main/docs/variability.md)). Gate on deterministic proxies instead: bytes of JavaScript transferred, images with dimensions, `font-display`, and CLS measured in the page with a generous ceiling. If Lighthouse runs at all, assert on its audit-based categories (Accessibility, Best Practices, SEO), not on Performance.
- **The classic SPA mistake is a soft 404.** A CloudFront or Cloudflare SPA fallback serves `index.html` with status 200 for every unknown path. Google calls that a soft 404 ([Google](https://developers.google.com/search/docs/crawling-indexing/http-network-errors)). A frozen test can require `GET /no-such-page` to return 404.
- **Prod smoke should hold the cheap, read-only, deterministic checks:** headers, HTTPS redirect, 404 status, a clean console, axe on the home page, and the meta tags. Lighthouse, the budgets and the keyboard walks belong on branch only.

## Markers that can't be tested automatically, and why

- **About 43% or more of accessibility issues.** By Deque's own count, axe finds 57%, and GDS found the best tool caught 41% of planted barriers ([Deque](https://www.deque.com/automated-accessibility-testing-coverage/), [GDS](https://accessibility.blog.gov.uk/2017/02/24/what-we-found-when-we-tested-tools-on-the-worlds-least-accessible-webpage/)). GOV.UK says tools "will not catch all errors" and asks for a manual WCAG 2.2 check with assistive technology ([GOV.UK](https://www.gov.uk/service-manual/technology/accessibility-for-developers-an-introduction)). Machines can't judge whether alt text is _meaningful_ (1.1.1), whether headings and labels _describe_ their content (2.4.6), whether link text makes sense in context (2.4.4), or what a screen reader actually announces.
- **Focus indicator quality.** A test can prove that _something_ changes when focus arrives. Whether it's noticeable is judgment under AA, because 2.4.7 "does not specify what that form is" ([Understanding 2.4.7](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)). The measurable size and contrast rule is 2.4.13, which is AAA.
- **INP and real-user Core Web Vitals.** The thresholds are defined at the field p75 over real visits ([web.dev](https://web.dev/articles/defining-core-web-vitals-thresholds)), and INP needs real input ([web.dev vitals](https://web.dev/articles/vitals)). A lab run is a proxy, not the metric.
- **Visual polish, typography and layout quality.** With no screenshot baselines, a test can't judge aesthetics. **Inference:** this is where a reviewer most often notices "junior" work, and it stays human-judged.
- **Copy quality and correctness of the bio content** beyond the exact strings the spec pins.
- **Progressive enhancement / no-JS baseline.** GOV.UK requires it for government services ([GOV.UK](https://www.gov.uk/service-manual/making-software/progressive-enhancement)). It _could_ be tested (`javaScriptEnabled: false`), but **Inference:** a client-rendered React SPA shows nothing without JavaScript unless it's prerendered. Whether to require prerendering is a spec decision, not a test-design question.
- **Security beyond headers:** XSS in chat rendering, secret handling, and dependency hygiene. Code review and the secret scan cover these. A black-box test can probe one known payload, but it can't prove an absence.
- **Lighthouse Performance as a pass/fail gate.** It can be run, but it isn't reliable on shared runners (see the table).

## Recommended short list for this episode

**Inference** throughout: this selection is mine. It ranks markers by documented authority, determinism and cost. Each line needs the spec to pin exact values, because the frozen lint forbids loose matchers.

**Prod smoke** (cheap, read-only, deterministic, and no chat sends, so no API spend):

1. **Headers on `/`:** HSTS, CSP (including `frame-ancestors`), `X-Content-Type-Options: nosniff`, `Referrer-Policy` and `Permissions-Policy`, each with `toBe(exact)`. Also `x-powered-by` is undefined.
2. **Caching:** `/` has `Cache-Control: no-cache`, and the first hashed JS asset has `max-age=31536000, immutable`.
3. **HTTP to HTTPS:** a 301 to the same host.
4. **A real 404:** an unknown path returns status 404 and shows the not-found heading.
5. **A clean console:** no console errors, page errors or failed same-origin requests on `/`.
6. **axe on `/`:** `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa` and `best-practice`, with no violations.
7. **Head metadata on `/`:** `lang`, an exact `<title>`, the meta description, the four required `og:*` tags, and `link[rel=icon]` returning 200.
8. **Reflow:** no horizontal overflow at 320px on `/`.

**Branch acceptance only** (adds per-route coverage and the slower checks):

9. Items 1–8 on **every route**, plus a unique title per route and each route loading directly by deep link.
10. **Keyboard:** the skip link works, the Tab order follows the spec through the nav and the chat, Escape closes the chat and returns focus to the launcher, and each tabbable control shows a visible focus change.
11. **Reduced motion:** with `reducedMotion: 'reduce'`, opening the chat runs no animations or transitions.
12. **Performance proxies:** JS transferred (encoded) is ≤ the spec's budget (170 KB is web.dev's starter number), every `img` has dimensions, every `FontFace.display` is in the allowed set, and in-page CLS is ≤ 0.1. LCP is < 4000 ms, as a coarse guard.
13. **Lighthouse non-performance categories** (Accessibility, Best Practices, SEO) all equal 1, from one run in a helper. Performance is reported but not gated, or gated with a median of 3 and a low floor. Leave SEO out if branch environments use `noindex`.
14. **Internal links:** every same-origin link returns 200. `robots.txt` and the sitemap (if specced) match exactly.

## Open questions

1. **How do deep routes return 200 and unknown routes return 404** on CloudFront/Cloudflare? The options are prerendering each route to its own `index.html`, an edge function that knows the route list, or Google's SPA fallback (redirect to a `/not-found` that returns 404, or `noindex`). The spec has to choose before item 4 can be frozen.
2. **Should branch environments be `noindex`** (a robots header or a `Disallow: /` robots.txt)? If they are, the robots.txt body and Lighthouse SEO differ by target, and with straight-line tests that means separate smoke and acceptance assertions, or a helper that returns the expected value for `FROZEN_TARGET`.
3. **CSP for the chat:** the chat calls `/api/chat` on the same origin, or on a separate API host? That decides `connect-src`. Vite's dev mode injects inline styles, but the production build normally doesn't. Confirm that no `style-src 'unsafe-inline'` is needed (Observatory scores it 0, not a penalty).
4. **Does the deploy enable CDN compression?** The JS budget measures encoded bytes. Without compression, the number reflects raw size, and the threshold should be set accordingly.
5. **Lighthouse in CI:** the runner has `workers: 1`, which matches Lighthouse's advice against concurrent runs. But the variability doc wants ≥ 2 dedicated cores, which GitHub-hosted runners may not guarantee. Is a non-gating, reported Performance score worth its roughly 10–20 s per URL (**Inference**, unmeasured)?
6. **Which WCAG level is the target?** AA is the norm (the [MoJ front-end standards](https://technical-guidance.service.justice.gov.uk/documentation/standards/justice-digital-front-end-engineering-standards.html) require WCAG 2.2 AA, as practice). Reduced motion (2.3.3) and Focus Appearance (2.4.13) are AAA, so including them is a deliberate step above.
7. **HSTS `preload` and `includeSubDomains`:** these affect every subdomain, including branch hosts, and preload is hard to undo. Does the owner want them on the apex domain?
8. **Contrast measurement.** Does the design use text over images or gradients, where axe returns `incomplete` instead of a verdict? If it does, a helper that samples pixels would be needed, or the spec accepts that gap.

## Sources on "junior vs senior" framing

- The searches turned up only career-advice and vendor blogs (for example greatfrontend.com and resumegeni.com). They aren't primary or authoritative, so this file doesn't rely on them.
- **Practice:** the UK Ministry of Justice front-end standards set WCAG 2.2 AA, support for zoom "up to 400%", a descriptive title per page, semantic HTML, and Lighthouse for monitoring. That figure is lower than Deque's 57%, and the two measure different things: Deque counts issues found in real audits, while MoJ's source isn't given.

- **Inference:** across these sources, "experienced" shows up less as cleverness and more as _deliberately configured defaults, verified_. The CloudFront managed security policy is a concrete example. It looks finished, but it still adds a deprecated header and sends no CSP ([AWS](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/using-managed-response-headers-policies.html)).
