# Getting better-looking web design from an AI coding agent

Research notes for the spec, gathered 2026-11-17. The setup: a personal portfolio site in React + Vite, built as a static frontend by Claude Code (Claude Opus or Sonnet 5.x) in **one autonomous run** from a written spec, with no human design review during the run. The layout is fixed in advance: a two-column, resume-style layout like brittanychiang.com, without its cursor spotlight. Frozen Playwright tests, written before the build, judge the run. No screenshot baselines exist.

Conventions in this file:

- Each claim links to its source. Text in quotation marks is quoted from that source.
- **Inference:** marks my own reasoning, which no source states.
- **Suggestion:** marks something I'm proposing for the spec or repo.
- **Vendor practice:** marks what a model vendor recommends for its own models. That's evidence of what works with that vendor's model, not a standard.

## TL;DR

- **Unguided models converge on a default look.** Anthropic calls the cause "distributional convergence": "Safe design choices–those that work universally and offend no one–dominate web training data" ([Anthropic blog](https://claude.com/blog/improving-frontend-design-through-skills)). For Opus 5.5 in particular, Anthropic says a general instruction like "avoid a generic AI look" "mostly swaps one default for another." What works is naming specific patterns to avoid, then checking what the first result used instead ([Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5#frontend-design-defaults)).
- **The strongest lever is a concrete spec.** Anthropic's Sonnet 5 guide says "The model follows explicit specs precisely." Its worked example pins the palette as five hex values, the corner radius, the type character, the section structure and the hover transition ([Prompting Claude Sonnet 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5)). OpenAI ([GPT-5.4 frontend post](https://developers.openai.com/blog/designing-delightful-frontends-with-gpt-5-4)) and Vercel ([v0 design systems](https://v0.app/docs/design-systems)) also push design tokens and real content up front.
- **Anthropic's `frontend-design` skill is the fullest first-party guidance.** It asks for a two-pass process: write a compact token plan, review it against the brief, then build. It also names five clusters of AI-default traits, and it asks the agent to screenshot and critique its own work ([SKILL.md](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md)).
- **A visual feedback loop is first-party advice from both Anthropic and OpenAI.** Claude Code's docs list "A browser screenshot next to the mockup" as a check Claude can run ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). OpenAI says "Playwright is particularly valuable for front-end development" ([OpenAI](https://developers.openai.com/blog/designing-delightful-frontends-with-gpt-5-4)).
- **Many quality floors can be checked objectively** with Playwright, `getComputedStyle` and axe-core. They include contrast, reflow at 320 px, focus visibility, target size, line length, how many font sizes, families and colors are used, values staying on a spacing grid, reduced motion, layout shift, banned fonts and colors, and the two-column geometry. **Taste can't be checked**: whether the result is distinctive, cohesive or well-proportioned needs a human or a model judge.
- **Watch out:** the reference site itself uses several of the traits that Anthropic's guidance calls defaults. Brittanychiang.com uses Inter, a near-black slate background with a single teal accent, `rounded-full` pill tags and uppercase tracked-out labels (see [Section 2.3](#23-deciding-about-the-reference-sites-own-tells)). The spec has to decide which of these to keep.

## 1. What the sources say works

### 1.1 Anthropic: the `frontend-design` skill

The same file is published in [anthropics/skills](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md) and as the `frontend-design` plugin in [anthropics/claude-plugins-official](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/frontend-design). I diffed the two copies on 2026-11-17 and they're identical. The [claude-code plugins README](https://github.com/anthropics/claude-code/blob/main/plugins/README.md) says Anthropic's plugins "are developed in claude-plugins-official." It was last changed on 2026-09-03 ([commit history](https://github.com/anthropics/skills/commits/main/skills/frontend-design/SKILL.md), [PR #1713](https://github.com/anthropics/skills/pull/1713): "Revises the frontend-design skill so generated interfaces look less templated").

Its key rules, quoted from the [current SKILL.md](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md):

- **Role and stance.** "Approach this as the design lead at a design studio known for giving every client a distinct visual identity… make deliberate, opinionated choices about palette, typography, and layout that are specific to this brief."
- **Subject first.** "The subject's industry, subject matter, materials, and vernacular are where distinctive visual choices come from." "Build with the brief's real content and subject matter throughout."
- **Typography.** "Typography carries the personality of the page… use one family or two, and if two, make them clearly distinct." "Choose your typefaces deliberately, not the default families you would reach for on any other project, and set a clear type scale following the default guidance of The Elements of Typographic Style." "Default to line lengths of less than 80 characters."
- **Typographic tells to avoid.** "Accenting just a single word or phrase in a headline", "Using all caps for labels", and "Adding unnecessary typographic labels above content."
- **Structure is information.** "Structural devices like outlines, borders, numbering, eyebrows, dividers, labels, etc., encode useful information about the content rather than decorate it." Numbered markers are only for content that "actually is a sequence — like a stepped process or a timeline."
- **Motion.** "Use non-user-triggered motion sparingly… fade-and-slide-up entrances on each section and hover transitions on every card are the generic default and read as AI-generated. Motion that answers a person's action… is welcome."
- **The five default clusters it calls tells**, quoted in full:
  1. "a warm cream background (near #F4F1EA) with a high-contrast serif display and a terracotta or warm-clay accent (often near #D97757…)"
  2. "a near-black background with a single bright acid-green or vermilion accent"
  3. "a broadsheet-style layout with hairline rules, zero border-radius, and dense newspaper-like columns"
  4. "the SaaS-card kit: content chopped into identical rounded cards, one border-radius on everything regardless of hierarchy, the same soft grey shadow (rgba(0,0,0,.1)) under each, and gradient washes as decoration"
  5. "template chrome…: a tracked-out ALL-CAPS eyebrow label above every heading; meta strings joined with middle dots ('A · B · C'); labels built as 'WORD — fragment' with a spaced em dash; tinted near-black (#0B0B0B, #111) standing in for black; a monospace face for small data labels; a '→' appended to link and button text."

  It adds: "Where the brief pins down a visual direction, follow it exactly — the brief's own words always win, including when it asks for one of these looks. Where it leaves an axis free, don't spend that freedom on one of these defaults."

- **Two-pass process.** "First, brainstorm a short design plan… create a compact token system with color, type, layout, and principles. Color: describe the core base palette as 4–6 named hex values. Type: the typefaces and their roles. Layout: … ASCII wireframes… Include alignment guidance." Then "review that plan against the brief before building: if any part of it reads like the generic default you would produce for any similar page… revise that part."
- **CSS hygiene.** "be careful of structuring your CSS selector specificities. It's easy to generate CSS classes that cancel each other out… This can happen often with padding/margin between sections."
- **Restraint and quality floor.** "Spend your boldness in one place." "Build to a quality floor without announcing it: responsive down to mobile, visible keyboard focus, reduced motion respected, visually accessible, harmonious color palettes." "Critique your own work as you build, taking screenshots to review if your environment supports it — a picture is worth 1000 tokens." "before leaving the house, take a look in the mirror and remove one accessory."
- **Copy.** "Copy can make a design feel as templated as the design itself." "Write from the end user's perspective." "Keep the tone conversational: plain verbs, sentence case, no filler."

**The skill has changed over time.** The December 2025 version ([commit 00756142ab](https://github.com/anthropics/skills/blob/00756142ab/skills/frontend-design/SKILL.md)) asked for a "BOLD aesthetic direction" and a flat ban: "NEVER use generic AI-generated aesthetics like overused font families (Inter, Roboto, Arial, system fonts), cliched color schemes (particularly purple gradients on white backgrounds)…". It also encouraged "scroll-triggering and hover states that surprise." The current version drops the named-font ban and the call for more motion. In their place it lists the default clusters above, which newer models produce, and it is much more restrained about motion. **Inference:** the purple-gradient and Inter defaults belong to earlier models. For Claude 5.x, the tells to guard against are the five clusters in the current file.

### 1.2 Anthropic: blog post and prompting docs

- **Blog post, "Improving frontend design through Skills"** (12 November 2025, by Anthropic's Applied AI team) ([source](https://claude.com/blog/improving-frontend-design-through-skills)):
  - It defines the problem: "During sampling, models predict tokens based on statistical patterns in training data. Safe design choices–those that work universally and offend no one–dominate web training data."
  - It gives a `<frontend_aesthetics>` prompt that targets four axes: typography, color and theme, motion and backgrounds. It lists things to avoid: "Overused font families (Inter, Roboto, Arial, system fonts)", "Clichéd color schemes (particularly purple gradients on white backgrounds)", "Predictable layouts and component patterns". It also warns: "You still tend to converge on common choices (Space Grotesk, for example) across generations."
  - On the results: "Typography alone leads to significant improvement", and "the mandate to use more interesting fonts seems to encourage the model to improve other aspects" of the design. The evidence is side-by-side examples. The post doesn't quantify the effect.
  - "Even with explicit instructions to avoid certain patterns, the model can default to other common choices."
- **Prompting best practices, "Frontend design" section** ([source](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). It repeats the `<frontend_aesthetics>` snippet and links the full skill. It says: "without guidance, models can default to generic patterns that create what users call the 'AI slop' aesthetic."
- **Prompting Claude Opus 5.5, "Frontend design defaults"** ([source](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5#frontend-design-defaults)). This is the most relevant one for this run. "Asked for frontend work without design direction, Claude Opus 5.5 falls back on a few default styles, and a general instruction such as 'avoid a generic AI look' mostly swaps one default for another. It responds well to instructions that name specific patterns to avoid… Work iteratively: check which styles the first result used instead, and extend the list if needed." Its example prompt happens to be a personal website: "Do not use a cream or off-white background, italic accent words in headlines, numbered '01/02/03' section labels, monospace labels, or pill-shaped buttons."
- **Prompting Claude Sonnet 5, "Design and frontend defaults"** ([source](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5)):
  - "Generic instructions ('don't use that color,' 'make it clean and minimal') tend to shift the model to a different fixed palette rather than producing variety."
  - "Two approaches work reliably: **1. Specify a concrete alternative.** The model follows explicit specs precisely". The example pins five hex values, a "4px corner radius consistently across cards, buttons, inputs, and media frames", the typeface character, the section order and "transition: all 160ms ease out". "**2. Have the model propose options before building.**" Ask for 4 directions, each as "bg hex / accent hex / typeface", and let the user pick one.
  - It says Sonnet 5 "interprets prompts literally" and "does not silently generalize an instruction from one item to another", so "state the scope explicitly."
- **Claude Code best practices** ([source](https://code.claude.com/docs/en/best-practices)):
  - "If you already have the thing Claude needs, hand it over instead of describing it… An image: paste the screenshot of the design."
  - "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually _is_ done, 'looks done' is all it has to go on." The checks it lists include "A [browser screenshot](https://code.claude.com/docs/en/chrome) next to the mockup."
  - "`be ambitious`" is the one phrase it says still helps, because Claude otherwise builds "the smallest thing that satisfies it."
  - For unattended runs: "Can it check its own work? The test suite, a `Stop` hook, some kind of review step."
- **The bundled `/run` and `/verify` skills** "launch your app and confirm changes against the running app instead of tests alone" ([Claude Code skills](https://code.claude.com/docs/en/skills)). The docs page doesn't mention a design-review skill bundled with Claude Code.
- **Opus 5.5 reads screenshots well.** It "reads visual material more accurately than Claude Opus 5 without extra tooling… It is better, too, where meaning depends on position rather than text… what changed between two versions of a diagram" ([Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)). **Inference:** this makes a self-screenshot critique loop more useful than it was on earlier models.
- **A related caution.** "Claude can sometimes focus too heavily on making tests pass at the expense of more general solutions" ([prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). **Inference:** frozen design tests can pull a run toward the cheapest design that passes them. Keep the checks to quality floors, and leave aesthetic direction to the spec.

### 1.3 OpenAI (Vendor practice, GPT models)

- **"Designing delightful frontends with GPT-5.4"** ([source](https://developers.openai.com/blog/designing-delightful-frontends-with-gpt-5-4); the page carries no date, and third-party coverage dates it to March 2026):
  - Underspecified prompts make models "fall back to high-frequency patterns from the training data."
  - Tokens: "Define core design tokens such as `background`, `surface`, `primary text`, `muted text`, and `accent`," with type roles such as display, headline, body and caption. It caps type at two typefaces unless there's a clear reason.
  - Its hard rules include: "The first viewport must read as one composition", "avoid default stacks (Inter, Roboto, Arial, system)", "Cards are allowed only when they are the container for a user interaction", "avoid purple-on-white defaults", and no more than one accent color without a strong existing system.
  - The litmus checks it has the model run on itself include: "Can the page be understood by scanning headlines only?", "Does each section have one job?", "Would the design still feel premium if all decorative shadows were removed?", and "If deleting 30 percent of the copy improves the page, keep deleting."
  - References: "instruct the model to first generate a mood board or several visual options before selecting the final assets." Reference screenshots help the model infer "layout rhythm, typography scale."
  - "Providing the model with real copy, product context, or a clear project goal" is among the simplest wins.
  - "Playwright is particularly valuable for front-end development." It lets the model inspect the rendered page, test viewports and compare against a reference UI.
  - The post links a `frontend-skill` in `openai/skills/.curated`. On 2026-11-17 that path returned 404, and no frontend skill was in the repo tree.
- **GPT-5 prompting guide, frontend section** ([source](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide)):
  - A `<self_reflection>` prompt has the model write itself a 5 to 7 category rubric for "a world-class one-shot web app", then iterate against it.
  - Its `<code_editing_rules>` say: "Limit typography to 4–5 font sizes and weights for consistent hierarchy"; "Use 1 neutral base (e.g., `zinc`) and up to 2 accent colors"; "Always use multiples of 4 for padding and margins to maintain visual rhythm"; and "The user interface must adhere to a consistent design system."
  - **Inference:** these are the most directly testable numbers any vendor publishes.
- **"Frontend with GPT-5" cookbook** ([source](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_frontend), now marked archived). It recommends a stack of Next.js, Tailwind, shadcn/ui and Motion, and it lists Inter and Geist among recommended fonts. That contradicts the later "avoid default stacks" rule. It also notes that "production use still requires review and iteration."

### 1.4 Vercel v0 (Vendor practice)

- **Design systems.** A registry is "a distribution specification designed to pass context from your design system to AI Models". Tokens live in `src/app/tokens.css`, and you "overwrite the colors… ensuring all the variable names remain unchanged". The registry "lets v0 generate prototypes that match your design system, without manual overrides" ([v0 design systems, legacy guide](https://v0.app/docs/design-systems)).
- **Prompting.** "the best prompts always include three core inputs": product surface, context of use, and constraints and taste. "Constraints tell v0 what not to invent." Constraints include style, layout expectations and color systems ([How to prompt v0](https://vercel.com/blog/how-to-prompt-v0), 15 December 2025).
- **Reference images.** "Drop in a screenshot with no instructions and v0 closely replicates its layout, colors, and components." Adding "use this as a guide" tells it "to reinterpret the image instead" ([v0 academy](https://vercel.com/academy/v0-foundations/enhance-design-with-screenshots-and-versions)). **Inference:** handing Claude a screenshot of brittanychiang.com risks the same near-copy. Say explicitly which parts to keep (the layout) and which to replace (palette, type, tags).

### 1.5 Google (Vendor practice)

Google publishes no frontend-aesthetics guidance for Gemini that I could find. Firebase Studio's prompting guide says to name a design system ("Use a clean and modern UI using Google Material Design principles"), to "Specify constraints on the UI", and to build incrementally ([Firebase Studio prompting](https://firebase.google.com/docs/studio/prompting)). The general Gemini prompt docs ask for "clear and specific instructions" ([Gemini prompt design](https://ai.google.dev/docs/prompt_best_practices)).

### 1.6 Design-system primitives

- **W3C Design Tokens (DTCG) Format Module 2025.10** is the first stable version, published 28 October 2025 ([announcement](https://w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/), [spec](https://www.designtokens.org/TR/2025.10/format/)). The spec says: "This specification is considered stable."
  - "An object with a **`$value`** property is a token." `$type` and `$description` are optional.
  - Types: `color`, `dimension`, `fontFamily`, `fontWeight`, `duration`, `cubicBezier`, `number`, plus the composites `typography`, `shadow`, `border`, `transition`, `strokeStyle` and `gradient`.
  - Dimensions are `{ "value": 16, "unit": "px" }`, in `px` or `rem`. Colors are `{ "colorSpace": "srgb", "components": [...] }` with an optional `hex`. Aliases are written `"{colors.blue}"`.
  - Files use `.tokens` or `.tokens.json`.
- **Tailwind v4** stores "design tokens" as theme variables in `@theme`, and "All of your theme variables are turned into regular CSS variables" on `:root`. The default `--spacing` is `0.25rem` (a 4 px step), and the default type scale runs from `--text-xs` (0.75rem) to `--text-9xl` (8rem) ([Tailwind theme docs](https://tailwindcss.com/docs/theme)).
- **USWDS spacing units** are "based on multiples of 8px", and "Any spacing value in utilities or component CSS should use the following spacing unit tokens" ([USWDS](https://designsystem.digital.gov/design-tokens/spacing-units/)).
- **Fluid type scales (Utopia).** "Define a type scale for a small screen", "Define a type scale for a large screen", then "interpolate between the two." The example uses ratio 1.2 at 320 px and 1.333 at 1500 px ([Utopia](https://utopia.fyi/blog/designing-with-fluid-type-scales/)). **Inference:** fluid sizes give continuous font-size values, which works against a "font size is one of N tokens" test unless the tests run at fixed viewports and compute the expected values.

### 1.7 Techniques compared

| Technique                                             | First-party support                                    | Notes                                                                                         |
| ----------------------------------------------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| Concrete spec (hex palette, fonts, radius, structure) | Anthropic Sonnet 5 guide: "works reliably"             | The single strongest lever in the sources                                                     |
| Named anti-pattern list                               | Anthropic Opus 5.5 guide, the skill, OpenAI hard rules | Generic "avoid AI look" doesn't work; named patterns do. Extend the list after seeing results |
| Plan tokens first, review the plan, then build        | Anthropic skill (two passes), OpenAI (tokens up front) | Fits a one-run build: the plan can be a committed file                                        |
| Propose several directions, pick one                  | Anthropic Sonnet 5 guide, OpenAI (mood board)          | Needs a chooser. In a no-human run, either the spec picks or the agent picks and records why  |
| Reference screenshot                                  | Claude Code docs, v0, OpenAI                           | v0 replicates closely unless told "use this as a guide"                                       |
| Self-screenshot and critique                          | Anthropic skill, Claude Code docs, OpenAI (Playwright) | Opus 5.5 vision makes this cheaper and more accurate                                          |
| Self-rubric                                           | OpenAI GPT-5 guide, OpenAI litmus checks               | Not in Anthropic's docs                                                                       |
| Hard check the agent can run                          | Claude Code docs ("Give Claude a check to run")        | Frozen tests serve as this, and the agent can run them locally                                |

## 2. What to put in the spec and the repo

All of these are **suggestions**.

### 2.1 In the spec: pin the axes, leave one free

The skill says the brief's words always win, and Sonnet 5 "follows explicit specs precisely". So every axis the spec pins is one the model can't spend on a default.

- **Suggestion:** a `## Visual design` section that pins:
  - **Palette:** 4 to 6 named hex values, with roles: background, surface, text, muted text, accent, and an optional second accent. This follows the skill's "4–6 named hex values", OpenAI's token list, and OpenAI's "1 neutral base… up to 2 accent colors". If dark and light themes are both wanted, give the set twice.
  - **Typefaces:** one or two families by name, with the role of each and how they're loaded (self-hosted `woff2` in the repo, so the static build has no third-party font requests). Name the fallback stack.
  - **Type scale:** an explicit list of sizes, such as 5 steps (OpenAI: "4–5 font sizes"), with line heights. Body line-height ≥ 1.5 (from [WCAG 1.4.8](https://www.w3.org/WAI/WCAG22/Understanding/visual-presentation.html), AAA).
  - **Spacing scale:** a 4 px base with named steps (Tailwind's default `--spacing: 0.25rem`, and OpenAI's "multiples of 4").
  - **Radius and shadow:** one or two radius values, and say whether shadows are used at all. That keeps the run out of the skill's "SaaS-card kit".
  - **Measure:** the body text column is no wider than about 70ch (skill: "less than 80 characters"; WCAG 1.4.8: "no more than 80 characters").
  - **Motion:** a short list of allowed motions (for example, link hover color, a focus ring transition and one page-load moment), and say that everything is off under `prefers-reduced-motion: reduce` ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)).
  - **The "one memorable thing":** name it in the spec, or say that the agent picks it and records it. This comes from the skill's "Spend your boldness in one place".
- **Suggestion:** a **named anti-pattern list**, written as the Opus 5.5 guide shows. Draw it from the skill's five clusters, and drop anything the spec deliberately keeps from the reference site. Possible entries: no cream or off-white page background; no `#D97757`-family terracotta accent; no italic or colored accent word in headlines; no "01/02/03" section numbers; no monospace labels; no `→` appended to link text; no middle-dot meta strings; no identical cards with the same soft shadow; no gradient washes; no scroll-triggered fade-up on every section.
- **Suggestion:** spell out the **layout geometry**, because it's fixed and testable: at desktop widths the header column is sticky and roughly 40 to 50% wide, and the content column scrolls; below the breakpoint the columns stack. Give the breakpoint in px. For reference, brittanychiang.com uses `lg:sticky lg:top-0 lg:max-h-screen lg:w-[48%]` inside `max-w-screen-xl` (from the page's HTML, fetched 2026-11-17).
- **Suggestion:** **real copy.** OpenAI says real content is one of the simplest ways to improve results, and the skill says to "Build with the brief's real content". `docs/research/portfolio-contents.md` already exists, so point the spec at the final text and don't let the run invent placeholder copy.
- **Suggestion:** say "**be ambitious**" about the quality floor (from the Claude Code docs), and list the floor explicitly. The Sonnet 5 guide says the model doesn't generalize instructions it wasn't given.

### 2.2 In the repo before the run

- **Suggestion:** a **DTCG token file** (`design/tokens.tokens.json`) holding the palette, type scale, spacing, radius and durations from the spec. The run then generates or hand-writes CSS custom properties from it. The frozen tests read the same file, so the spec, the code and the tests share one source of truth. Use DTCG because it's the stable W3C community format ([spec](https://www.designtokens.org/TR/2025.10/format/)). **Inference:** a mechanical token-to-CSS step, whether a small script or Style Dictionary, makes "every computed color comes from a token" testable.
- **Suggestion:** **vendor the `frontend-design` skill** into `.claude/skills/frontend-design/` at a pinned commit (currently [`41bbe19d1a`](https://github.com/anthropics/skills/commit/41bbe19d1a)), so the run's guidance doesn't change mid-series. Note that the skill's own process says to "confirm with the client" and to make "aesthetic risk" choices. In a no-human run, the spec has to say that the spec stands in for the client, and which axes stay open.
- **Suggestion:** a **reference screenshot** of the target layout, at desktop and mobile widths, labelled as **layout only**. Write "use this as a guide for structure; do not copy its palette, typeface or tags" (from v0's replicate-versus-reinterpret finding). A wireframe works too, and avoids the copying risk. **Open question:** the licensing of committing a screenshot of someone else's site to a public repo.
- **Suggestion:** a **self-critique step** in `/attempt` or the spec: after the build, run Playwright to screenshot `/` at 1440×900, 768×1024 and 375×812, in both color schemes if dark mode is in scope. Read the screenshots, check them against the spec's visual section and the anti-pattern list, fix, and repeat a bounded number of times. Sources: the skill's "taking screenshots to review", the Claude Code docs' screenshot check, and OpenAI's Playwright advice. **Inference:** cap the loop at two or three passes. That mirrors the Opus 5.5 guide's advice to stop automatic continuations "after two or three", which it gives for a related problem.
- **Suggestion:** a **design-plan file** that the run writes before coding: the skill's token plan, ASCII wireframe and "what I changed and why" review. It gets committed with the PR, which gives the retro something to read about the run's design choices.
- **Suggestion:** have the run **execute the frozen design checks locally** before it opens the PR. The Claude Code docs call this "the single most useful line in your `CLAUDE.md`" when it's the command that runs the checks.

### 2.3 Deciding about the reference site's own tells

From the page's HTML (fetched 2026-11-17): `body class="bg-slate-900 … text-slate-400"`, an accent of `text-teal-300`, the tag class `rounded-full bg-teal-400/10 px-3 py-1 text-xs … text-teal-300` (37 times), section labels `text-sm font-bold uppercase tracking-widest` (marked `lg:sr-only`, so they show only on mobile), nav labels `text-xs font-bold uppercase tracking-widest`, and a footer that says "All text is set in the Inter typeface." Measured against the guidance above:

| Reference-site trait                                    | Flagged by                                                                      |
| ------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Inter                                                   | Anthropic 2025 skill and blog, Sonnet 5 snippet, OpenAI GPT-5.4 post            |
| Near-black slate background with one bright teal accent | Skill cluster 2 ("near-black background with a single bright… accent"), roughly |
| `rounded-full` pill tech tags                           | Opus 5.5 example ("pill-shaped buttons"; these are tags, not buttons)           |
| Uppercase tracked-out labels                            | Skill ("Using all caps for labels", cluster 5)                                  |

The frozen lint bans branches in test files (`frozen/README.md`), so any measuring logic goes in `frozen/helpers/` and tests assert on its result with `toEqual` or numeric matchers. **Inference:** most of these checks are a helper that runs `page.evaluate` over visible elements and returns a list of violations, and the test asserts that the list is `[]`.

## 4. What can't be checked automatically

- **Distinctiveness.** Whether the page reads as "a choice made for this specific brief" or as a default (the skill's core test). Ban lists only rule out known defaults. The Opus 5.5 guide says the model then moves to another default, and only a human or model judge catches that.
- **Cohesion and harmony.** Whether the palette and type pairing feel like one system. The skill lists "harmonious color palettes" as part of the floor, but there's no metric. Checks #14 to #21 keep the token set small and consistently used, which is necessary but not sufficient.
- **Hierarchy and proportion.** Whether the eye lands on the right thing first, whether whitespace is balanced, whether the sticky column and content column feel proportioned. OpenAI's litmus questions ("one strong visual anchor?", "understood by scanning headlines only?") are judgments.
- **The "one memorable thing".** Whether it exists, and whether it's tasteful.
- **Copy quality.** The skill's writing rules (user's perspective, plain verbs, no filler) can be partly linted (sentence case, banned filler words), but whether the copy is good can't.
- **Contrast over images or gradients.** Axe reports these as `incomplete`. A pixel-sampling helper could close part of the gap.
- **Motion quality.** Tests can count animations and check that reduced motion turns them off, but they can't judge whether an easing or timing feels right.

**Inference:** a **model judge** (Claude reading screenshots against a written rubric) could score some of these. That would be non-deterministic and so doesn't fit the frozen-test model (Q40 allows one retry). If used at all, it suits the retro or `/scorecard`, reported as information and not as a gate.

## 5. Open questions

1. **Which reference-site traits stay?** Inter, the slate and teal palette, pill tags and uppercase labels (see [Section 2.3](#23-deciding-about-the-reference-sites-own-tells)). Each needs a keep-or-replace decision in the spec.
2. **Who picks the direction in a no-human run?** The spec, fully pinned (Sonnet 5 approach 1), or the agent, from a set of proposals it writes into the design-plan file (approach 2, with the agent as chooser). Pinning everything makes the run predictable. Leaving one axis free is where the skill says distinctiveness comes from.
3. **Vendor the skill, or write a project skill?** The upstream skill changed twice in 2026 (June and September). Pinning a commit keeps runs comparable across the series.
4. **Fluid or fixed type?** A fluid (`clamp()`) scale fits the Utopia approach, but it makes check #14 depend on the viewport. Fixed steps at breakpoints are easier to test.
5. **How strict are the grid checks?** "Every spacing is a multiple of 4" may fail on legitimate values (`1px` borders, `0.5rem` with non-16px roots, line-height-driven gaps). An allowlist or tolerance needs deciding before the tests freeze.
6. **Is AAA in scope?** Checks #12, #13 and #23 cite AAA criteria (1.4.8, 2.3.3). They're good floors for a text-heavy portfolio, but they go beyond WCAG AA.
7. **Screenshot licensing.** Can a screenshot of brittanychiang.com be committed to a public repo as a layout reference, or should it be a hand-drawn wireframe instead?
8. **OpenAI's `frontend-skill`** is linked from its blog post but returned 404 on 2026-11-17. It may have moved. It's not needed for a Claude run.
