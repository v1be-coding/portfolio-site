# React good practices for a prerendered, hydrated React + Vite site

Research notes for the spec, gathered 2026-11-17. The stack is react and react-dom 19.3.1, vite 8.3.6, @vitejs/plugin-react 6.2.1, eslint-plugin-react-hooks 7.1.1 and typescript 6.0.3, with no router yet. Four pages (`/`, `/v1be-coding`, `/v1be-coding/portfolio-site` and the 404) are prerendered at build time and hydrated with `hydrateRoot`. The Chat is closed in the HTML and calls `/api/health` in an effect, the theme follows the system setting, and the CSP has `script-src 'self'`. Frozen Playwright tests fail on any console error, page error or failed same-origin request.

Conventions in this file:

- Each claim links to its source. Text in quotation marks is quoted from that source.
- **Inference:** marks my own reasoning, which no source states.
- **Verified:** marks something I ran locally on 2026-11-17 against the exact package versions: Chromium from Playwright 1.65.0 (the version in `frozen/package.json`), a react-dom 19.3.1 bundle built with esbuild in both production and development mode, and ESLint 10.13.0 with eslint-plugin-react-hooks 7.1.1 `configs.flat.recommended` (the preset `eslint.config.js` already uses for `src/web/**`). The probes were throwaway scripts in the scratchpad, and none of them are in the repo.
- Package source is cited at its exact version on unpkg, for example [react-dom-client.production.js @19.3.1](https://unpkg.com/react-dom@19.3.1/cjs/react-dom-client.production.js).

## TL;DR

- **In a production build, a hydration mismatch is a page error, not a console error.** React reports recoverable errors through `window.reportError` by default ([source](https://unpkg.com/react-dom@19.3.1/cjs/react-dom-client.production.js), `defaultOnRecoverableError`; [changelog 18.0](https://github.com/facebook/react/blob/main/CHANGELOG.md)). **Verified:** a text or structure mismatch fires Playwright's `pageerror` with `Minified React error #418`. So the frozen suite must capture `pageerror` as well as `console` type `error`. `frozen/helpers/fixtures.ts` already records `pageerror` as evidence.
- **In a production build, an attribute mismatch is silent and is never fixed.** Only the dev build warns ("A tree hydrated but some attributes ... didn't match ... This won't be patched up"), and it warns with `console.error` ([source](https://unpkg.com/react-dom@19.3.1/cjs/react-dom-client.development.js), `emitPendingHydrationWarnings`). **Verified:** in production, `<p class="s">` stays `s` after the client renders `className="c"`, and nothing is logged. A frozen test against the deployed build can't catch this class of bug through the console, so it needs a DOM assertion instead (see "Enforcement").
- **The draft's CSP rule is half right.** React sets the `style` prop through the CSSOM (`style[name] = value` and `style.setProperty`), which CSP doesn't gate. But the _prerendered HTML_ contains `style="..."` attributes, and strict `style-src` blocks those. **Verified:** Chromium logs a console error ("Applying inline style violates the following Content Security Policy directive 'style-src 'self''"). Either avoid `style` props in anything that's prerendered, or allow `style-src-attr 'unsafe-inline'`.
- **`vite build` emits no inline `<script>` for a plain `index.html` entry.** The modulepreload polyfill is bundled into the entry chunk ([Vite docs](https://vite.dev/config/build-options#build-modulepreload); [source](https://unpkg.com/vite@8.3.6/dist/node/chunks/node.js)), so `script-src 'self'` holds. Vite does inline assets under 4 KiB as `data:` URIs by default, so either set `build.assetsInlineLimit: 0` or allow `data:` in `img-src` and `font-src` ([Vite CSP](https://vite.dev/guide/features#content-security-policy-csp)).
- **The lint catches less impurity than you'd expect.** The `purity` rule flags only `Date.now()`, `performance.now()` and `Math.random()`. **Verified:** `new Date()`, `typeof window`, `window.innerWidth`, `localStorage` and `matchMedia` in render all pass the recommended preset. The preset also flags react.dev's own "two-pass rendering" pattern (`useEffect(() => setIsClient(true), [])`) through `set-state-in-effect`, and the react.dev source marks that example as an expected compiler error ([hydrateRoot.md source](https://github.com/reactjs/react.dev/blob/main/src/content/reference/react-dom/client/hydrateRoot.md)).
- **React 19.3 adds `use(browser())`** for browser-only subtrees. During prerender it leaves the nearest `<Suspense>` fallback in the HTML, and the client then renders the real content "without reporting a recoverable error" ([changelog 19.3.0](https://github.com/facebook/react/blob/main/CHANGELOG.md); [react.dev `browser`](https://react.dev/reference/react-dom/browser)). This is the documented replacement for the `isClient` effect.

## The corrected rule list

Each rule has its source and a one-line "why".

### R1. Render is pure and deterministic: the build and the first client render produce the same output

Don't read `Date` (including `new Date()` and `toLocaleDateString()`), `Math.random`, `performance.now`, `window`, `document`, `navigator`, `localStorage`, `matchMedia`, `location`, `import.meta.env.SSR` or `typeof window` during render. Do browser-only work in `useEffect`, in event handlers, or behind `use(browser())`.

- Sources: "`hydrateRoot()` expects the rendered content to be identical with the server-rendered content. You should treat mismatches as bugs and fix them." ([react.dev hydrateRoot, Caveats](https://react.dev/reference/react-dom/client/hydrateRoot#caveats)). Its list of common causes includes "Using checks like `typeof window !== 'undefined'` in your rendering logic" and "Using browser-only APIs like `window.matchMedia` in your rendering logic" ([Hydrating server-rendered HTML](https://react.dev/reference/react-dom/client/hydrateRoot#hydrating-server-rendered-html)). "`new Date()` is not idempotent ... Similarly, functions like `Math.random()` also aren't idempotent" ([Rules of React: idempotent](https://react.dev/reference/rules/components-and-hooks-must-be-pure#components-and-hooks-must-be-idempotent)).
- Vite: `import.meta.env.SSR` "is statically replaced during build" ([Vite SSR guide](https://vite.dev/guide/ssr#conditional-logic)). **Inference:** branching on it in render is the same bug as `typeof window`, because the SSR build and the client build take different branches.
- Correction to the draft: put locale-dependent formatting (`Intl`, `toLocale*`) on the list too. React's own mismatch message names "Date formatting in a user's locale which doesn't match the server" ([source](https://unpkg.com/react-dom@19.3.1/cjs/react-dom-client.development.js), `throwOnHydrationMismatch`). **Inference:** the safest approach is to format any dates (Experience dates, Scorecard dates) to fixed strings at build time, with an explicit locale and time zone.
- Why: the user sees the build-time HTML first, and React attaches to it. If the first client render differs, React throws away and regenerates the tree, or, for attributes, silently leaves the wrong value in place.

### R2. The theme is CSS only: `prefers-color-scheme` plus `color-scheme`

Use CSS custom properties switched by `@media (prefers-color-scheme: dark)`, and declare `color-scheme: light dark` (or `<meta name="color-scheme" content="light dark">`). Don't compute the theme in JavaScript during render, and don't add an inline "no-flash" theme script.

- Sources: `color-scheme` changes "the canvas surface", "scrollbars" and "form controls", and "Component authors must use the `prefers-color-scheme` media feature to support the color schemes on the rest of the elements" ([MDN color-scheme](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/color-scheme)). `matchMedia` in render is a named mismatch cause ([react.dev hydrateRoot](https://react.dev/reference/react-dom/client/hydrateRoot#hydrating-server-rendered-html)).
- Correction to the draft: add `color-scheme`. Without it, form controls and scrollbars stay light in dark mode. **Inference:** the usual inline "read the theme before paint" `<script>` would also break `script-src 'self'`, which is one more reason the theme has to be CSS only.
- Why: CSS resolves the theme before first paint on both sides, so the markup is the same for every visitor, and there's nothing to mismatch.

### R3. Initial state is identical on both sides, and any data the HTML used ships with it

`useState` initialisers, context defaults and store snapshots must give the same value at build time and on the first client render. The Chat starts closed (`open = false`) and must not restore an "open" state from `localStorage` during render. If a page needs build-time data, the client must import the same data module (bundled), not refetch it.

- Sources: "Rendering different data on the server and the client" is a listed cause ([react.dev hydrateRoot](https://react.dev/reference/react-dom/client/hydrateRoot#hydrating-server-rendered-html)). For `useSyncExternalStore`, "The server snapshot must be the same between the client and the server" ([useSyncExternalStore](https://react.dev/reference/react/useSyncExternalStore#adding-support-for-server-rendering)).
- Gotcha: react.dev suggests "emit a `<script>` tag during server rendering that sets a global like `window.MY_STORE_DATA`" (same page). **Inference:** that's an inline script, which `script-src 'self'` blocks. So bundle the data as a module, or emit `<script type="application/json">` and read it with `JSON.parse`. A data block isn't executed, so `script-src` doesn't apply to it.
- Why: the health status, the panel state and the content all go into the first render. Anything only the browser knows has to arrive after hydration, in an effect.

### R4. The same route and tree on both sides: one `hydrateRoot` on the prerendered root, no stray whitespace

- The client must resolve the same route from `location.pathname` that the prerender used for that file. That includes the 404 page, which the host serves at arbitrary URLs.
- Call `hydrateRoot` once, on the same element the prerender filled, with the same wrapper tree (`<StrictMode>`, providers) and the same `identifierPrefix` if one is set.
- The template must not add whitespace inside the root: use `<div id="root"><!--app-html--></div>` on one line.

Sources:

- "The React tree you pass to `hydrateRoot` needs to produce **the same output** as it did on the server". The first listed cause is "Extra whitespace (like newlines) around the React-generated HTML inside the root node" ([react.dev hydrateRoot](https://react.dev/reference/react-dom/client/hydrateRoot#hydrating-server-rendered-html)).
- "You'll likely have only one `hydrateRoot` call in your app" ([Caveats](https://react.dev/reference/react-dom/client/hydrateRoot#caveats)).
- `identifierPrefix` "Must be the same prefix as used on the server" ([Parameters](https://react.dev/reference/react-dom/client/hydrateRoot#parameters)).
- Vite's React SSR template uses `<div id="root"><!--app-html--></div>` and wraps both entries in `<StrictMode>` ([create-vite-extra template-ssr-react](https://github.com/bluwy/create-vite-extra/tree/master/template-ssr-react)).

**Inference:** the trap here is trailing slashes and base paths. If the host serves `/v1be-coding/index.html` at `/v1be-coding/`, and the client router matches only `/v1be-coding`, the client renders the 404 tree over the page HTML, and that's a mismatch (`#418`). The 404 page has the same risk: its HTML is served at `/no-such-page`, so the client must fall through to the same Not-found component. Normalise the pathname identically in both entries, and test each route with and without a trailing slash.

- Why: if the route or tree differs, the whole page mismatches. `useId` values also depend on the tree shape ("`useId` requires an identical component tree on the server and the client", [useId](https://react.dev/reference/react/useId#generating-unique-ids-for-accessibility-attributes)).

### R5. Valid HTML nesting

No block content in `<p>` (no `div`, `ul`, headings or the like). No interactive content inside `<a>` or `<button>` (no `a` in `a`, no `button` in `a`). No `<a>` or `<button>` inside a `<button>`. No text directly in `<ul>` or `<table>`.

- Sources: `p`'s content model is "Phrasing content", and the parser closes an open `p` when it sees a start tag such as `div` ("If the stack of open elements has a p element in button scope, then close a p element") ([HTML spec, p element](https://html.spec.whatwg.org/multipage/grouping-content.html#the-p-element); [HTML spec, in body](https://html.spec.whatwg.org/multipage/parsing.html#parsing-main-inbody)). `a` is "Transparent, but there must be no interactive content descendant, a element descendant, or descendant with the tabindex attribute specified" ([HTML spec, a element](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-a-element)), and a nested `<a>` start tag is a "Parse error" handled by the adoption agency algorithm ([in body](https://html.spec.whatwg.org/multipage/parsing.html#parsing-main-inbody)). `button` is "Phrasing content, but there must be no interactive content descendant" ([HTML spec, button](https://html.spec.whatwg.org/multipage/form-elements.html#the-button-element)).
- React: the dev build logs `console.error` "In HTML, %s cannot be a descendant of <%s>.\nThis will cause a hydration error." ([source](https://unpkg.com/react-dom@19.3.1/cjs/react-dom-client.development.js)). The production build has no nesting check (`grep` finds 0 matches).
- **Verified:** with `<p><div>` in production, the parser splits the build-time HTML, and the client throws `#418` (HTML) as a `pageerror`. In development the same case logs both the nesting `console.error` and the hydration `pageerror`.
- Why: the browser rewrites invalid HTML while parsing, so the DOM no longer matches what React rendered, even though the HTML string did.

### R6. `useId` for every generated id (`aria-controls`, `aria-labelledby`, `htmlFor`), never a counter or `Math.random`, and never as a list key

- Sources: "useId is generated from the 'parent path' of the calling component. This is why, if the client and the server tree are the same, the 'parent path' will match up regardless of rendering order", and "**Do not call `useId` to generate keys in a list**" ([useId](https://react.dev/reference/react/useId)).
- 19.x format: `useId` returns `_R_<tree>_` when hydrating and `_r_<n>_` for client-only ids ([source](https://unpkg.com/react-dom@19.3.1/cjs/react-dom-client.development.js), `mountId`). 19.1 changed the format to valid CSS selectors, and 19.2 switched to underscores ([changelog](https://github.com/facebook/react/blob/main/CHANGELOG.md)).
- Correction to the draft: static ids are fine for one-per-page singletons. Writing `id="chat-panel"` in the Chat is deterministic and simpler. **Inference:** `useId` is needed only when a component can appear more than once, or when the frozen tests shouldn't depend on the id. Tests should find elements by role and name, not by a `useId` value, because those values aren't stable API.
- Why: a counter or a random id differs between the build and the client, which causes an attribute mismatch. In production that's silent, and it leaves `aria-controls` pointing at nothing.

### R7. Every referenced asset exists, and there are no 4xx responses on page load

This covers every `src`, `href`, CSS `url()`, font, `favicon`, `manifest` and `og:image`.

- Vite only warns when an HTML-referenced asset is missing ("doesn't exist at build time, it will remain unchanged to be resolved at runtime") ([source](https://unpkg.com/vite@8.3.6/dist/node/chunks/node.js)). Files under `public/` aren't checked at all, so the build doesn't enforce this rule.
- **Verified:** in Chromium, a 404 or 503 `fetch` (or `<img>`) logs `console.error` "Failed to load resource: the server responded with a status of 404 (Not Found)", but it does **not** fire Playwright's `requestfailed`. `requestfailed` is only for requests that got no response.
- **Inference:** headless Chromium didn't request `/favicon.ico` in my probe, but desktop browsers do. Ship a real favicon and link it, so real users don't get a console 404.
- Why: a missing asset is a console error in the frozen suite, and an obvious defect on the live site.

### R8. CSP: `script-src 'self'` with no inline scripts, and an explicit decision on style attributes

- Scripts: Vite's build adds the modulepreload polyfill by prepending `import "vite/modulepreload-polyfill"` to the entry's proxy module ("The polyfill is auto injected into the proxy module of each `index.html` entry", [build.modulePreload](https://vite.dev/config/build-options#build-modulepreload); [source](https://unpkg.com/vite@8.3.6/dist/node/chunks/node.js)). So no inline script is emitted, and `polyfill: false` isn't needed for CSP. The plugin-react Fast Refresh preamble is an inline `<script type="module">`, but it's injected only in dev ([plugin-react source](https://unpkg.com/@vitejs/plugin-react@6.2.1/dist/index.js)).
- Styles, CSSOM: CSP3 gates only CSS that is _parsed from a string_ ("insert a CSS rule", "parse a CSS declaration block": "all invocations of CSSOM's various `cssText` setters and `insertRule` methods") ([CSP3 §6.1.13 style-src](https://w3c.github.io/webappsec-csp/#directive-style-src)). HTML applies CSP when the `style` content attribute "is added or has its value changed" ([HTML spec, the style attribute](https://html.spec.whatwg.org/multipage/dom.html#the-style-attribute)). CSSOM property setters re-serialise into the attribute with the "updating flag" set, and the attribute change steps return early when it is set, "to avoid serialize-and-reparse on style attribute" ([CSSOM §6.6](https://drafts.csswg.org/cssom/#update-style-attribute-for)). MDN puts it plainly: "styles properties that are set directly on the element's `style` property will not be blocked", whereas `setAttribute("style", ...)` and `style.cssText = ...` are blocked ([MDN style-src](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/style-src)). **Inference:** that chain of spec steps is my reading; the browser test below confirms the result.
- React's client sets styles with `style[styleName] = value` and `style.setProperty(...)` for `--custom` properties ([source](https://unpkg.com/react-dom@19.3.1/cjs/react-dom-client.production.js), `setValueForStyle`), so client-side style updates are not blocked. But the server renderer writes `' style="'` into the HTML ([source](https://unpkg.com/react-dom@19.3.1/cjs/react-dom-server.node.production.js)), and the parser gates that attribute. **Verified:** an HTML `style` attribute under `style-src 'self'` logs a console error and isn't applied, while `el.style.color = ...` and `el.style.setProperty('--x', ...)` log nothing.
- `style-src-attr` "specifies valid sources for inline styles applied to individual DOM elements", and it falls back to `style-src` when it's absent ([MDN style-src-attr](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/style-src-attr)).
- Corrected rule: pick one of the following and write it into the spec.
  - (a) **No `style` prop in any prerendered markup.** Use classes and CSS custom properties from stylesheets. Keep `style-src 'self'` strict. This is the stricter option.
  - (b) Allow `style-src-attr 'unsafe-inline'` and keep `style-src-elem 'self'`.
  - Either way, don't let `data:` into `script-src`, and handle Vite's `data:` asset inlining ([Vite CSP](https://vite.dev/guide/features#content-security-policy-csp)).
- Why: a CSP violation is a console error, so it fails the frozen suite, and an unapplied style is a visual bug.

### Rules to add

- **R9. Effects must work when run twice, and fetches must handle failure without throwing.** Every effect that fetches (`/api/health`) needs a cleanup that ignores stale results, plus a `.catch` or `try`/`catch`. Sources: "your components should be resilient to being remounted" and the race-condition cleanup pattern ([You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect#fetching-data)). Strict Mode re-runs effects in development ([StrictMode](https://react.dev/reference/react/StrictMode)), and 19.3 also does it "during hydration" ([changelog 19.3.0](https://github.com/facebook/react/blob/main/CHANGELOG.md)). **Inference:** an unhandled rejection (a network error, or `AbortError` from an `AbortController` cleanup) becomes a `pageerror`. A health check that renders "down" on failure, rather than throwing, keeps the console clean when the API is down.
- **R10. Prefer `use(browser())` inside `<Suspense>` over an `isClient` effect** for genuinely browser-only UI. Sources: "You can use this instead of checking `typeof window`, waiting for an Effect to set mounted state", and "`use(browser())` must be inside a `<Suspense>` boundary during server rendering. Without one, the server render fails." When React leaves the fallback, "it does not call the server renderer's `onError` callback or `hydrateRoot`'s `onRecoverableError` callback" ([react.dev browser](https://react.dev/reference/react-dom/browser)). The Chat panel's _closed_ state should still be server-rendered (R3); only content that truly needs the browser goes behind `browser()`.
- **R11. Use `prerenderToNodeStream` (or `prerender`) from `react-dom/static` for the build step, not `renderToString`, if anything suspends.** Source: "`renderToString` returns a string immediately, so it does not support waiting for data to load for static HTML generation. If you use Node.js, use `prerenderToNodeStream`" ([renderToString](https://react.dev/reference/react-dom/server/renderToString)), and "`prerender` waits for all data to load before resolving" ([prerender](https://react.dev/reference/react-dom/static/prerender)). Both exports exist in `react-dom/static` 19.3.1 ([static.node.js](https://unpkg.com/react-dom@19.3.1/static.node.js)). **Inference:** with no Suspense data, `renderToString` gives the same HTML and is simpler. The choice only matters if `use(browser())` or `use(promise)` appears.
- **R12. Keep `<StrictMode>` in both entries.** Its checks are "development-only and do not impact the production build" ([StrictMode](https://react.dev/reference/react/StrictMode)), and the Vite template wraps both entries in it. It has to wrap both, or the trees differ (R4).
- **R13. Don't use `suppressHydrationWarning` except for a genuinely unavoidable single-element difference.** "This only works one level deep, and is intended to be an escape hatch. Don't overuse it. React will **not** attempt to patch mismatched text content." ([Suppressing unavoidable hydration mismatch errors](https://react.dev/reference/react-dom/client/hydrateRoot#suppressing-unavoidable-hydration-mismatch-errors)). **Inference:** on a fully static site there should be no such case, so the spec can ban it.
- **R14. `useLayoutEffect` is allowed, but it has to be a deliberate choice.** React 19 removed the server warning ("Remove layout effect warning on server", [changelog 19.0](https://github.com/facebook/react/blob/main/CHANGELOG.md)). The string no longer appears anywhere in react-dom 19.3.1's bundles, but the troubleshooting text is still on [useLayoutEffect](https://react.dev/reference/react/useLayoutEffect#im-getting-an-error-uselayouteffect-does-nothing-on-the-server). It still never runs at build time, so anything it measures can't be in the HTML.

- Listen to all three of `page.on('pageerror')`, `page.on('console')` filtered to `type() === 'error'`, and `page.on('requestfailed')` filtered to same origin. Each catches a class the others miss: hydration errors and unhandled rejections arrive as `pageerror`, CSP violations and HTTP 4xx/5xx as `console`, and dropped connections as `requestfailed`.
- `requestfailed` also fires for `net::ERR_ABORTED` when a test navigates away while `/api/health` is in flight. Either wait for the health response before navigating, or exclude `ERR_ABORTED` deliberately.
- The dev React build prints a `console.info` DevTools banner. That's not an error, and it doesn't appear in production. Frozen tests run against the deployed production build, so dev-only warnings (attribute mismatches, nesting warnings) **never appear there**.

### What the ESLint preset actually contains (7.1.1)

Read from the package source ([eslint-plugin-react-hooks.development.js @7.1.1](https://unpkg.com/eslint-plugin-react-hooks@7.1.1/cjs/eslint-plugin-react-hooks.development.js)), not just the docs:

- Error: `rules-of-hooks`, plus the compiler rules `config`, `error-boundaries`, `gating`, `globals`, `immutability`, `preserve-manual-memoization`, `purity`, `refs`, `set-state-in-effect`, `set-state-in-render`, `static-components` and `use-memo`.
- Warn: `exhaustive-deps`, `unsupported-syntax` and `incompatible-library`.
- `recommended-latest` adds `void-use-memo`.
- [react.dev](https://react.dev/reference/eslint-plugin-react-hooks) lists `component-hook-factories` as recommended, but in 7.1.1 it's a deprecated no-op (`makeDeprecatedRule('7.1.0')`).
- The `purity` rule's message is "Cannot call impure function during render", and its known-impure list is `Date.now`, `performance.now` and `Math.random`.
- `lint-staged` runs ESLint with `--max-warnings=0` (`package.json`), so `exhaustive-deps` warnings block commits in practice.
- **Verified** lint results for patterns in render:
  - Flagged: `Date.now()`, `Math.random()`, `ref.current++`, `setState(...)` in render, and `setState` synchronously in an effect body.
  - Not flagged: `new Date()`, `new Date().toLocaleDateString()`, `typeof window ? ... : ...`, `localStorage.getItem`, `window.matchMedia`, `useState(() => Math.random())`, `useSyncExternalStore(sub, () => true, () => false)`, and `setState` inside a `fetch().then` or `async` function in an effect.

## Gotchas specific to React 19.3 and Vite 8

1. **Production mismatches arrive as `pageerror` with a minified message.** `#418` with `args[]=text` or `args[]=HTML`, linking to `https://react.dev/errors/418` (**Verified**). A test failure won't show the diff. Reproduce with a dev build (`vite build --mode development`, or the dev SSR server) to get "Hydration failed because the server rendered text didn't match the client ..." with a `+ Client` / `- Server` diff ([React 19 blog](https://react.dev/blog/2024/12/05/react-19)).
2. **There's no `console.error` for a mismatch in either mode by default.** The text/structure mismatch goes through `onRecoverableError`, whose default is `reportError` ([source](https://unpkg.com/react-dom@19.3.1/cjs/react-dom-client.production.js)). MDN: `reportError()` reports errors "emulating an uncaught JavaScript exception" ([MDN reportError](https://developer.mozilla.org/en-US/docs/Web/API/Window/reportError)). Only the dev attribute-mismatch and nesting warnings use `console.error`. **Inference:** don't pass a custom `onRecoverableError` that swallows errors, or the frozen suite goes blind. If you add one for logging, have it call `reportError(error)` too.
3. **Attribute mismatches aren't patched.** "There are no guarantees that attribute differences will be patched up" ([Caveats](https://react.dev/reference/react-dom/client/hydrateRoot#caveats)). **Verified:** the server value stays in the DOM in production. That covers `aria-expanded`, `class`, `href`, `id` and `hidden`.
4. **react.dev's two-pass `isClient` example fails this repo's lint.** `set-state-in-effect` is an error in the recommended preset (**Verified**), and the docs source annotates that example with `expectedErrors: {'react-compiler': [7]}`. Use `use(browser())` inside `<Suspense>` (19.3+) or `useSyncExternalStore` with a `getServerSnapshot` instead.
5. **`use(browser())` needs a `<Suspense>` ancestor**, or the prerender fails ([react.dev browser](https://react.dev/reference/react-dom/browser)). `prerenderToNodeStream` gained an `onBrowserBailout` option to observe it ([prerenderToNodeStream](https://react.dev/reference/react-dom/static/prerenderToNodeStream)).
6. **Strict Mode double-invokes effects during hydration in 19.3 dev** ([changelog 19.3.0](https://github.com/facebook/react/blob/main/CHANGELOG.md), #35961). Locally `/api/health` is called twice on load, and in production once. **Inference:** a frozen API-call budget measured against production should expect one call per page load.
7. **React 19 skips unexpected tags in `<head>` and `<body>`** when hydrating the whole document, which makes it tolerant of extensions ([React 19 blog](https://react.dev/blog/2024/12/05/react-19)). **Inference:** hydrating `#root` rather than `document` keeps Vite in charge of `<head>` (asset links, the CSS `<link>`). That's simpler with a Vite-processed `index.html` template.
8. **The `useId` format changed twice in 19.x** (`:r1:` to `«r1»` to `_r_1_`; [changelog](https://github.com/facebook/react/blob/main/CHANGELOG.md)). Never hard-code one in a test or in CSS.
9. **19.3 fixed false-positive mismatches on `nonce`** (#37030) and **enabled Trusted Types integration** ([changelog 19.3.0](https://github.com/facebook/react/blob/main/CHANGELOG.md)). **Inference:** neither matters unless the CSP adds nonces or `require-trusted-types-for`.
10. **Vite inlines assets under 4096 bytes as `data:` URIs** (`build.assetsInlineLimit`, [build options](https://vite.dev/config/build-options#build-assetsinlinelimit)). Under `img-src 'self'` or `font-src 'self'` they're blocked, and the browser logs a console error. Set `assetsInlineLimit: 0` or allow `data:` for those directives only ([Vite CSP](https://vite.dev/guide/features#content-security-policy-csp)).
11. **Vite's SSR build is a second `vite build --ssr <entry>`** whose output is imported by a prerender script. The client build's `dist/.../index.html` is the template, "since it contains the correct asset links" ([Vite SSR guide](https://vite.dev/guide/ssr#building-for-production)). The guide's pre-render pointer is a Vue example ([prerender.js](https://github.com/vitejs/vite-plugin-vue/blob/main/playground/ssr-vue/prerender.js)), and the React template uses `renderToString` ([template-ssr-react](https://github.com/bluwy/create-vite-extra/tree/master/template-ssr-react)). **Inference:** if the spec wants per-route preload links, `build.manifest` or `--ssrManifest` is needed. With four small pages and one entry chunk, it probably isn't.
12. **A missing asset is a warning, not a build error, in Vite** (see R7). The build passes, and the frozen console capture is the backstop.
13. **The dev server injects inline scripts and styles** (the plugin-react preamble and CSS HMR `<style>` tags). **Inference:** don't apply the production CSP to `vite dev`, and don't judge CSP compliance from dev.

## Open questions for the spec

1. **Style attributes:** is the rule "no `style` prop in prerendered markup, `style-src 'self'`" (strict) or "`style-src-attr 'unsafe-inline'`" (lenient)? This decides whether a frozen test greps `dist/**/*.html` for `style=`.
2. **Trailing slashes and base path:** which form is canonical for `/v1be-coding` (with or without the slash), and does the other one redirect (301) or serve the same HTML? The router and the frozen route list both depend on it.
3. **Router:** add one, or use a four-entry `pathname → page` map? **Inference:** a map shared by the prerender script and the client entry removes a whole class of R4 bugs, and four static pages don't need client-side navigation. Plain `<a href>` full page loads hydrate each page fresh.
4. **Health check failure:** when `/api/health` is down, what does the Chat show, and is the browser's "Failed to load resource" console line for that one URL an allowed exception in the frozen console filter? If not, the API needs to answer 200 with a body that says it's down. That's a contract decision.
5. **Attribute-mismatch test:** should the frozen suite compare build-time HTML with the hydrated DOM for a fixed list of attributes (`aria-expanded`, `hidden`, `class` on the Chat tab, the `href`s)? It's the only way to catch production-silent mismatches.
6. **Build-time checks:** should the spec require a post-build script that fails on (a) inline `<script>` without `src`, (b) unresolved `src`/`href` in `dist`, and (c) `style=` under option (a)? These are cheap and deterministic, but they live outside `frozen/`.
7. **`prerenderToNodeStream` vs `renderToString`:** only matters if `use(browser())` or Suspense data is used. Pick one in the spec, so the build step is predictable.
8. **Locale and dates:** fixed locale and time zone (for example `en-GB`, `UTC`) for every date the pages show, formatted at build time?
9. **`suppressHydrationWarning` and custom `onRecoverableError`:** ban both outright? **Inference:** both can hide exactly what the frozen suite exists to catch.
10. **Per-page `<title>` and meta:** written into the template by the prerender script, or rendered with React 19's `<title>` hoisting? I didn't verify how `renderToString` into `#root` treats hoisted metadata, so pin this down before the frozen title tests are written.
